# 补丁点定位：从写死偏移到指令流解析

[补丁工程化](./patching-principles)讲了「怎么改」；这篇讲「改在哪」。

两者的区别在于：**特征码命中 ≠ 布局没变**。命中只说明那串字节存在，不说明它周围的结构还是你上次看到的样子。

## 写死偏移的三种死法

拿到特征码命中地址 `hit` 之后，最容易顺手写下的三类偏移：

```c
BYTE *jneva   = hit + 4;           // ① 特征码内部的相对位置
BYTE *hookva  = hit + 0x0F;        // ② 命中点之后的「已知距离」
DWORD gLo     = modbase + 0x1E4CF8; // ③ 全局变量相对模块基址
```

| 偏移 | 死法 |
| --- | --- |
| ① | 特征码本身就含这条 `jne` 的字节，位置是**确定的**——这类偏移其实安全，前提是特征码里真的包含了它 |
| ② | 作者在两段之间插一条指令，`hit` 仍命中，`hit + 0x0F` 落到指令中间 |
| ③ | 全局变量挪了位置，写入变成随机破坏 |

第二种最阴险：特征码校验**通过了**，补丁也「成功」了，程序却在别处崩。

## 二次定位：把距离解析出来

已知的跳转位置往往紧跟一条 `call rel32`：

```text
hit+0x00   83 7D FC 01          cmp dword [ebp-4], 1
hit+0x04   0F 85 1D 02 00 00    jne 失败分支
hit+0x0A   E8 xx xx xx xx       call 解析函数        ← 5 字节
hit+0x0F   8B 5D F8             mov ebx, [ebp-8]     ← 想 hook 的位置
```

`hit+0x0F` 等于 `hit + 4 + 6 + 5`，而这个 `5` 是 `call rel32` 的长度。

所以：

```c
BYTE buf[6];
ReadProcessMemory(hp, hit + 10, buf, 6, NULL);
if (buf[0] != 0xE8) return 0;        // 不是 call rel32 -> 布局变了，拒绝
BYTE *hookva = hit + 10 + 5;         // 解析出来的，不是猜的
```

同理，被 hook 的位置要校验**原始字节**：

```c
static const BYTE PROLOGUE[6] = { 0x8B,0x5D,0xF8, 0x83,0xC3,0x18 };
if (memcmp(buf, PROLOGUE, 6) != 0) return 0;
```

## 全局变量地址也能解析

这是最容易被忽略的一处。想往一个全局变量写值，通常是在周边指令里「看见」它的地址：

```asm
A3 F8 4C 1E 10        mov [0x101E4CF8], eax
89 15 FC 4C 1E 10     mov [0x101E4CFC], edx
```

`A3` 是 `mov [imm32], eax`，`89 15` 是 `mov [imm32], edx`。两条相邻，相差 4 字节——正好拼成一个 64 位值。

```c
int i_lo = -1, i_hi = -1;
DWORD lo = 0, hi = 0;
for (SIZE_T i = 0; i + 6 <= span; i++) {
    if (i_lo < 0 && buf[i] == 0xA3) {
        memcpy(&lo, buf + i + 1, 4);
        i_lo = (int)i;
        continue;
    }
    if (i_lo >= 0 && i_hi < 0 && buf[i] == 0x89 && buf[i + 1] == 0x15) {
        memcpy(&hi, buf + i + 2, 4);
        i_hi = (int)i;
        break;
    }
}
if (i_lo < 0 || i_hi < 0) return 0;
if (hi != lo + 4) return 0;          // 不相邻 -> 不是这个结构，拒绝
*resume = hookva + i_hi + 6;         // 第二条指令之后 = 原流程继续处
```

:::tip 相邻性校验是免费的过滤器

`hi == lo + 4` 这一条几乎不花成本，却能挡掉「扫到了别的 `A3` 指令」的误判。

类似的廉价校验还有：地址落在模块的映像范围内、地址 4 字节对齐、每个模块恰好命中 N 次。

:::

## 三道闸

把「校验」从「写之前的最后一步」提升成「分阶段的准入条件」：

| 闸 | 检查 | 不过时 |
| --- | --- | --- |
| 1 | 命中数量在合理区间 | 中止，报实际数量 |
| 2 | 命中点相对模块基址的偏移是已知值 | 中止，报实际偏移 |
| 3 | 每条命中的指令结构能完整解析 | 中止，报卡在哪一步 |

### 闸 1 不该写成「恰好等于」

```c
#define MIN_COPIES 1
#define MAX_COPIES 2
```

为什么用区间而不是精确值：如果目标带壳，**解包是渐进进行的**，关键模块的多份副本可能在窗口出现之后才陆续展开。

第一版写成「恰好 2 处」，实测在冷启动时只扫到 1 处，被误判成「目标已更新」直接中止——而它只是还没解包完。

配套的办法是**重扫**：

```c
for (int retry = 0; retry < 2 && (nl < MAX_COPIES); retry++) {
    Sleep(1500);
    nl = scan_collect(...);          // 再扫一遍
}
```

### 闸 2 才是真正的版本判据

偏移指纹比命中数量可靠得多：

```c
if (lh[i].at - modbase != 0x17EE) return -1;   // 这个模块里它就该在这个位置
```

数量会受时序影响，偏移不会。

### 闸 3：全部解析成功才开始写

```c
LOGIN_PLAN plans[8];
for (int i = 0; i < nl; i++)
    if (!plan_login(hp, lh[i].at, &plans[i])) return -1;   // 任一失败 -> 整体放弃

for (int i = 0; i < nl; i++) apply_login(hp, &plans[i]);   // 全部成功才动手
```

**先收集、再校验、最后统一写**。绝不「扫到一个改一个」——那样第一处失败时，前面的已经改完了，留下半截状态。

## 写入顺序与回滚

一处补丁往往由多个写入点组成（比如「NOP 掉跳转」+「装上 hook」）。这两步之间有中间态。

选择原则：**让每个中间态对客户端都是无害的**。

```c
// 先装 hook：此时跳转还在，hook 只在「条件成立」的路径上执行，行为不变
if (!write_code(hp, hookva, hook, 6)) return 0;

// 再 NOP 跳转：这一步之后才有行为变化
if (!write_code(hp, jneva, nop6, 6)) {
    write_code(hp, hookva, orig_hook, 6);   // 失败就把前一步撤回
    return 0;
}
```

反过来的顺序（先 NOP 再装 hook）会产生一个「条件恒成立但 hook 还没装」的窗口：客户端走进了本该写数据的路径，而写数据的代码还没就位。

## stub 里的指针校验

注入的代码经常要「读一个指针、往它的结构体里写值」。

```asm
mov ebx, [ebp-8]           ; ebx = 指针
mov dword [ebx+0x18], VALUE
```

如果 `[ebp-8]` 还没被初始化，`ebx` 就是栈上的垃圾值，这一步直接崩。

加几字节判断：

```asm
mov  ebx, [ebp-8]
cmp  ebx, 0x00010000       ; 低于用户态最小地址
jb   skip
cmp  ebx, 0x80000000       ; 高于 32 位用户态上限
jae  skip
mov  dword [ebx+0x18], VALUE
skip:
; 不依赖指针的写入放在 skip 之后，始终执行
```

`:jb` / `:jae` 是 8 位相对跳转，回填偏移时注意**基准是指令结束位置**：

```c
code[jb_op + 1] = skip_pos - (jb_op + 2);
```

:::warning 这类校验经常被当成「多余」

它的价值在于：**它把「必须满足某个前置条件」从用户输入转移到了代码本身**。

原版逻辑要求「输入必须 32 位以上」时的真正原因往往是「解析函数不跑完，结构体就是空的」。把校验做进 stub 之后，前置条件不再依赖用户行为。

:::

## 一个自检工具的价值

把「解析 + 构造」的逻辑抽到单独的头文件里，写一个**不需要目标程序**的自检：

```text
[1] 解析：在一段合成指令上验证 gLo/gHi/resume 正确；全局量不相邻时拒绝
[2] 构造：验证字节布局、两个 rel8 落点、rel32 回跳精确
[3] 执行：真的调用一遍生成的 stub，验证「条件为假时也走到成功路径」
```

第 3 步最关键。用一段手写的 `asm` 搭出真实栈帧，把一个假指针塞进 `[ebp-8]`，然后看：

- 正常指针 → 结构体被写对
- 野指针 `0x100` → 不崩、结构体不写、其余写入照常

这类自检跑一遍只要几秒，但能把「rel32 基准算错」「rel8 回填差 2 字节」这类问题在集成前全部暴露。**在没有目标程序的环境里能验证的部分，一定要先验证掉。**

## 小结

```text
特征码命中           -> 只是「这里像我找的东西」
偏移指纹             -> 才是「这里就是我要改的东西」
指令流解析           -> 才知道「改哪个字节」
先收集后写入          -> 才保证「不改半截」
stub 内自校验         -> 才不依赖「调用者一定准备好了」
```

补丁的稳定性不取决于你改得多准，而取决于**改错的时候能不能不出事**。
