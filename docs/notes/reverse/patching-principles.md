# 补丁工程化

定位到逻辑之后，改动的方式决定了这个补丁是「能跑」还是「能稳定跑」。这篇讲补丁的粒度选择、安全校验和常见陷阱。

:::note 前提

下面讨论的是**对自己的程序、教学样本、或有明确授权的目标**做修改。补丁技术本身是中性的，用在什么目标上决定了它是否正当。

:::

## 三种粒度

按副作用从小到大排：

### 1. 改跳转（最安全）

把条件跳转的指令字节改成 NOP（`0x90`）。

```asm
; 改前
cmp  dword [ebp-4], 1
jne  0x10001a15        ; 0f 85 1d 02 00 00

; 改后
cmp  dword [ebp-4], 1
nop nop nop nop nop nop
```

**适用条件**：目标分支不依赖中间变量。也就是"不管什么情况都往下走"是安全的。

**为什么最安全**：不改变任何寄存器、标志位、栈的状态，只是让一条指令失效。

:::warning 短跳转要注意长度

`jne` 有短（`75 xx`，2 字节）和近（`0f 85 xx xx xx xx`，6 字节）两种形式。
改成 NOP 时**必须填满原指令的字节数**，否则后面的指令会平移错位，整个函数就废了。

:::

### 2. 改比较

让条件判断恒定成立，但保留跳转指令。

```asm
; 改前：只有当 [ebp-4] 等于 1 时才走成功路径
cmp  dword [ebp-4], 1

; 改后：自己跟自己比，ZF 恒为 1（相等），跳转必然不成立
cmp  dword [ebp-4], [ebp-4]
```

**适用条件**：目标是让某个 `jcc` 恒定落到"继续往下走"。

**代价**：`cmp reg, imm8` 是 3 字节，`cmp reg, reg` 是 2 字节，**字节数对不上**。需要凑数——补一个 NOP，或者挑指令长度恰好相等的等价写法。

:::tip 用真值恒等式

技术上能凑出"结果恒定、长度可控"的写法，比如 `xor eax, eax` 让标志位归零、
或 `sub reg, reg`。但**每换一种写法都要重新核对指令长度**，别凭记忆。

:::

### 3. 注入 stub（最灵活，风险最高）

在代码段找一块空白区域（或者新分配一页），写一段自己的代码，然后用 `jmp` 接进去、再 `jmp` 跳回原流程。

```asm
; 原位置
jmp  my_stub           ; e9 rel32，5 字节

; my_stub 里
; ...干自己的事...
jmp  back_to_normal    ; 回到原流程下一条指令
```

**适用场景**：需要写多个变量、或者需要在原流程之外做额外计算时。

**必须注意的三件事**：

1. **栈平衡**。`push` 了几次就要 `pop` 几次，否则函数返回时 `ret` 会跳到错误地址。
2. **寄存器保护**。原流程可能正在用某个寄存器存重要值，stub 里改动了就得先 `push` 保存、`jmp` 回去前 `pop` 恢复。
3. **指令缓存**。写代码段之后要刷新指令缓存，否则 CPU 可能还在执行旧指令。

```c
VirtualProtectEx(hProc, addr, size, PAGE_EXECUTE_READWRITE, &oldProt);
WriteProcessMemory(hProc, addr, payload, size, NULL);
VirtualProtectEx(hProc, addr, size, oldProt, NULL);
FlushInstructionCache(hProc, addr, size);   // <-- 别漏
```

## 特征码校验

**永远不要无脑写死地址。** 换一个版本，地址全变，硬写会把程序写坏。

正确做法是"先确认这是我要改的地方，再动手"：

```c
// 1. 读目标位置现有字节
BYTE buf[N];
ReadProcessMemory(hProc, target, buf, N, NULL);

// 2. 跟预期特征码比对
if (memcmp(buf, EXPECTED_SIG, N) != 0) {
    // 不是这个版本 / 已经打过 / 布局变了
    return -1;
}

// 3. 确认无误才写
WriteProcessMemory(hProc, target, patch, N, NULL);
```

特征码怎么取：

| 做法 | 稳定性 |
| --- | --- |
| 取整个函数的前 16 字节 | 高，但可能因编译器优化而变 |
| 取 `cmp` + `jcc` 那 8~12 字节 | 中高，需延长避免误匹配 |
| 取单个指令的 2 字节 | 低，几乎必然误匹配 |

:::danger 特征码太短的后果

两段不同的逻辑，指令开头可能完全一样。比如两处都是

```text
8B 45 F4  89 45 FC  83 7D FC 01  0F 85 ...
```

只是后面跟的跳转偏移不同。如果你只取到 `0F 85` 就停，**会同时匹配到两处**——本该改 A 的结果把 B 也改了，或者改到了根本不相干的地方。

**规则：特征码必须包含区分这两处的那个字节。** 宁可长一点。

:::

## 多副本问题

某些程序会把同一模块映射到多个地址（一个正常执行、一个用于完整性比对），或者把关键代码复制到动态分配的内存里。

**验证方法**：补丁打完后如果行为没变，或者在另一条路径上行为异常，先在内存里搜一遍特征码，看看有几处命中。

```text
命中 0 处  -> 特征码不对，或者地址算错了
命中 1 处  -> 正常
命中 2+ 处 -> 都要打
```

## 补丁的管理方式

补丁少的时候随手写没问题，一旦超过三处，就该用表驱动：

```c
typedef struct {
    const char *name;
    uintptr_t   rva;
    const BYTE *sig;
    size_t      sig_len;
    const BYTE *patch;
} Patch;

static const Patch PATCHES[] = {
    { "login-check",   0x17F2, SIG_LOGIN,  sizeof(SIG_LOGIN),  NOP6 },
    { "unbind-check",  0x720D, SIG_UNBIND, sizeof(SIG_UNBIND), NOP6 },
};
```

**好处**：改一处补丁只改一行；漏打补丁会立刻暴露（补丁数量对不上）；每处都能独立校验和记录结果。

## 验证顺序

:::tip 从便宜到贵

1. **手工验证**：先在已经跑起来的进程上单点改（用调试器或简易工具），确认行为符合预期
2. **小工具验证**：写个只做打补丁的程序，不掺业务逻辑
3. **集成**：最后才把补丁放进正式流程

跳过前两步直接集成，是耗时最多的做法——出问题时你分不清是补丁错了、还是加载流程错了。

:::

## 一个附录：什么时候该停止打补丁

有些检查**不该绕**。

如果某个校验后面还跟着"按这个值分配缓冲区""按这个值决定循环次数"之类的代码，强行跳过校验不会解决问题，只会让程序在更远的地方崩溃（越界访问、空指针）。

这时正确做法是**让数据满足校验要求的形态**，而不是让校验失效。找找有没有更上游、影响面更小的位置可以改。
