# 运行时分析：字符串定位法

代码在磁盘上被加密了，但**程序跑起来之后，内存里的东西一定是明文的**——这是运行时分析的全部基础。

这篇讲一个通用套路：**从界面文案反推代码位置**。它不需要调试器、不需要脱壳、不需要重建导入表。

## 思路

编译后的程序里，字符串和引用它的代码是绑定的。指令需要用到字符串地址时，会把这个地址作为一个立即数编进指令里：

```asm
push 0x100B6FD7        ; 把字符串地址压栈
call MessageBoxA
```

所以有个稳定的推断链：

```text
字节序列（GBK/UTF-8 编码的文案）
    ↓ 在全内存中搜索
字符串的虚拟地址
    ↓ 把这个地址写成 4/8 字节小端，再搜一遍
引用它的指令的位置
    ↓ 反汇编该位置附近
完整的判断逻辑
```

这个方法的适用面很广：任何「界面上能看到一句提示」的程序都能用。而绝大多数程序——尤其是带界面的——恰好都有大量可读的提示文案。

## 第一步：把文案转成字节

关键是**编码要对**。Windows 上的中文程序常见三种：

| 编码 | 场景 | 示例 |
| --- | --- | --- |
| GBK / GB2312 | 老的 ANSI 程序、部分国产开发工具 | 易语言、Delphi |
| UTF-16LE | Win32 的 `W` 系列 API | 现代 C++ 程序 |
| UTF-8 | 跨平台程序、新版工具链 | Rust、Go |

```python
text = '登录失败'

print('GBK     :', text.encode('gbk').hex())
print('UTF-16LE:', text.encode('utf-16-le').hex())
print('UTF-8   :', text.encode('utf-8').hex())
```

搜的时候三种都试一遍，找到哪种命中，也就顺便知道了程序用的什么编码。

:::tip 选什么文案

优先选：

- **界面上稳定出现的**、不太可能被拼接出来的完整句子
- **有一定长度的**（4 个汉字以上），太短容易误命中
- 最好选那句**只有在一类情况下才会出现**的话——它周围的代码就一定是那类逻辑

:::

## 第二步：在目标进程内存中搜索

两个思路：

**思路 A：用调试器/工具的内置搜索**

x64dbg 有内存搜索功能（`Ctrl+B` 搜字节序列），IDA 连上调试器后也能搜。适合手工、一次性的探索。

**思路 B：自己写扫描器**

需要批量做、或者要扫描器不受反调试影响时，自己读进程内存更可控：

```c
// 通过 ReadProcessMemory 遍历目标进程的可读区域
// 伪代码，核心是 VirtualQueryEx + 过滤
MEMORY_BASIC_INFORMATION mbi;
for (LPCVOID addr = 0; VirtualQueryEx(hProc, addr, &mbi, sizeof(mbi)); addr =
         (LPBYTE)mbi.BaseAddress + mbi.RegionSize) {
    if (mbi.State != MEM_COMMIT) continue;
    if (!(mbi.Protect & (PAGE_READONLY | PAGE_READWRITE | PAGE_EXECUTE_READ |
                         PAGE_EXECUTE_READWRITE)))
        continue;

    // 读出来搜目标字节序列
}
```

拿到的是**字符串的虚拟地址**（VA）。

## 第三步：找引用点

把上一步得到的 VA，**按小端序写成 4 字节**（32 位程序）或 8 字节（64 位程序），再全内存搜一遍。

例如字符串在 `0x100B6FD7`：

```text
d7 6f 0b 10
```

搜到的每一个位置，都是一条**把该地址写进指令的**指令的一部分。命中最常见的形式：

```asm
push 0x100B6FD7            ; 68 d7 6f 0b 10
mov  ecx, 0x100B6FD7       ; b9 d7 6f 0b 10
mov  eax, offset 0x100B6FD7 ; b8 d7 6f 0b 10
lea  eax, [0x100B6FD7]     ; 8d 05 d7 6f 0b 10
```

命中位置往前推 1 个字节就是指令起始（因为操作数通常紧跟在操作码后面）。

## 第四步：读上下文

单看一条 `push` 看不出什么。**要 dump 命中点前后几十字节，然后反汇编**。

x64dbg 里直接在「转到 → 表达式」输入地址，就能看到周围的完整指令流。

典型的发现长这样：

```asm
; ...若干前置处理...
cmp  dword [ebp-4], 1        ; 拿某个结果码跟 1 比较
jne  error_path              ; 不等于 1 就跳到错误处理
; 成功路径
call do_success_stuff
```

关键点在于：**判断通常是一个 `cmp` + 一个条件跳转**。找到这个跳转，就找到了整段逻辑的分岔口。

## 多语言与"分支检测器"识别

同一类提示往往不止一句。比如一个程序可能同时有：

```text
"登录成功"
"登录失败"
"账号不存在"
"密码错误"
```

对**每一句**都做一遍上述流程，会把同一个函数里的多个分支都标出来。几轮之后就得到一张完整的分支表：

| 地址 | 条件 | 走向 |
| --- | --- | --- |
| `+0x1A0D` | `[ebp-4] == 2` | 「密码错误」 |
| `+0x1A15` | 其他 | 「登录失败」 |
| `+0x1A3D` | `== 1` | 「登录成功」 |

## 为什么值得用这个方法

对比一下几种路线：

| 路线 | 前提 | 耗时量级 | 成功把握 |
| --- | --- | --- | --- |
| 静态反汇编 | 未加壳 | 分钟~小时 | 高 |
| 脱壳 | 找到脱壳点 | 小时~天 | 中，虚拟化壳基本无解 |
| 重建导入表 | 壳不是太重 | 小时 | 中 |
| **字符串定位** | **程序能跑起来** | **小时** | **高** |

字符串定位的"代价"是它只能覆盖**用到这些文案的代码**。但实践中，一个功能的入口处几乎总有提示文案，所以顺着文案能摸到绝大部分感兴趣的逻辑。

## 几个实践中容易踩的坑

:::warning 注意

- **编码错了搜不到**。GBK 和 UTF-16 都试，别默认 UTF-8。
- **字符串被拆开存储**。有些程序把长文案分段存放，或运行时拼接。这时选短一点的片段。
- **多份模块副本**。程序可能把同一模块映射了两份（一份用于正常执行，一份用于校验）。两处都要看。
- **地址会变**。开启 ASLR 后每次加载的基址不同。记录时记 **RVA**，不要记 VA。

:::
