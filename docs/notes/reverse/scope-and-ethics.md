# 边界与合规

这个栏目只记录**分析方法**。写之前先明确界限，对读者和作者都好。

## 什么属于可以公开讨论的

- PE 结构、文件格式、汇编与指令编码
- 加壳的原理与识别特征（不加壳本身）
- 运行时观察的通用思路、调试器用法
- 补丁的技术手法与工程原则
- 算法分析、协议结构、编码规则
- 对**自己的软件**、**教学样本**、**CTF 题目**、**有授权目标**的一切分析

这些内容在教科书、RE 社区、安全会议上都是公开讨论的。

## 什么不适合公开发布

- 针对具体商业软件的绕过方法、补丁字节、特征码
- 完整的分发链路（破解成品、注册机、激活绕过工具）
- 配合上述内容的 "使用说明"
- 未公开漏洞的利用细节

区别在哪？**前者讲的是"这类问题的一般解法"，后者是"这个产品的这扇门怎么撬"。**

同一个技术点，写进方法论文里是知识；配上特定产品的地址、特征码、成品文件，就变成了针对那个产品的操作指南。

## 关于授权

以下情况分析是正当的：

| 场景 | 说明 |
| --- | --- |
| 自己的软件 | 包括你参与开发、持有源码或版权的 |
| 明确授权 | 委托方书面同意、渗透测试合约、漏洞赏金项目范围 |
| 教学/研究样本 | 公开的 crackme、CTF 题目、教学用二进制 |
| 互操作性研究 | 为兼容性目的分析文件格式或协议（需符合当地法律） |
| 恶意软件分析 | 安全研究场景下分析样本行为 |

**"我想用它但不想付费"不在这个列表里。**

## 记录时的自我检查

写笔记之前问自己：

1. 这篇里的内容，能不能直接照着做去绕过某个具体产品？
2. 有没有出现某款真实产品的地址、特征码、补丁字节？
3. 如果目标作者看到了这篇，他会认为这是**研究**还是**攻击**？

第三问最实用。把它当成一条红线：**如果对方看到会觉得被针对了，那就不该公开。**

## 结语

逆向工程本身是一门正经的技术——安全研究、恶意软件分析、兼容性实现、遗留系统的维护，都依赖它。

方法可以公开，目标要挑清楚。
