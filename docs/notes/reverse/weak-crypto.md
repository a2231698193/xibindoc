# 弱加密的识别

逆向里遇到的「加密」大部分不是密码学，是**混淆**。两者的区别不在于算法复不复杂，而在于**密钥从哪来**。

如果密钥能从客户端发出去的数据里算出来，这套加密的强度就等于密钥的长度。

## 先分类

| 类型 | 表现 | 破解成本 |
| --- | --- | --- |
| 编码 | Base64、Hex、URL 编码 | 一眼就能认出来 |
| 固定密钥 XOR | 密文有周期性重复 | 几分钟 |
| **可变密钥 XOR（密钥可从明文推）** | 每次密文不同，但密钥熵很低 | **半小时** |
| 真流密码（RC4/AES-CTR） | 密钥来自握手或内置常量 | 数天，通常不值得 |
| 非对称 + 签名 | 有公钥、有验签 | 基本不可破 |

真正值得花时间的只有第三类：**看起来每次都不一样，实际上密钥空间小得可怜**。

## 判断是不是单字节 XOR

对同一段密文，用 0~255 每个值试一遍 XOR，然后**给结果打分**。

```python
def xor_score(data, key):
    out = bytes(b ^ key for b in data)
    printable = sum(1 for b in out if 32 <= b < 127 or b in (9, 10, 13))
    zeros = out.count(0)
    # 可打印字符多 + 全零字节多 = 越像明文
    return printable + zeros * 2

best = max(range(256), key=lambda k: xor_score(cipher, k))
print(hex(best), bytes(b ^ best for b in cipher))
```

打分函数不用很聪明。真实的明文（尤其带结构的数据）几乎一定会在「可打印 + 连续零」这两项上明显胜出，而随机密钥解出来全是不可打印字节。

:::tip 用已知明文反推，而不是暴力

如果协议里有你知道一定会出现的内容——固定的 JSON 字段、路径前缀、协议魔数、填充的零——直接拿它反推密钥更快：

```text
0x28 ^ ord('{')  = key
```

而且这样得到的密钥可以立刻用于解码整段，比逐个试更可靠。

:::

## 周期性重复 = 密钥短

把密文按步长分组，统计相同位置上字节的重复率：

```python
def repeat_rate(data, step):
    cols = [data[i::step] for i in range(step)]
    return sum(len(set(c)) for c in cols) / len(data)   # 越小越像固定周期
```

`step=1` 的得分明显低于其它值，说明是单字节密钥；`step=4` 明显低，说明是 4 字节循环密钥（很可能是 `DWORD` 密钥或反复 XOR 一个 32 位常量）。

## 关键一步：从多组样本反推密钥公式

这是最容易卡住、也最容易一步跨过去的地方。

**现象**：每次会话的密钥都不一样，但都能从报文里某几个字节推出来。

**做法**：收集 N 组 `(报文, 正确密钥)` 对，然后**从最简单的组合开始试**。

```python
samples = [
    (bytes.fromhex('3bcbc0314442407c'), 0x38),
    (bytes.fromhex('43fe9dfed5d3d14a'), 0x9f),
    (bytes.fromhex('e9455eb5141210ca'), 0xde),
]

def try_xor(a, b):
    return all(blob[a] ^ blob[b] == key for blob, key in samples)

for i in range(8):
    for j in range(8):
        if i != j and try_xor(i, j):
            print(f'key = nonce[{i}] ^ nonce[{j}]')
```

输出：

```text
key = nonce[4] ^ nonce[7]
```

**7 组样本全部命中**——这不是巧合，是公式。

:::danger 别假设复杂算法

人的直觉是「两个字节异或太简单了，不可能」。但现实里大量商业软件的「加密」就是这么简单：开发者要的是**不让人一眼看懂**，不是抵抗密码分析。

从 `xor` 相邻字节开始，依次试 `sum`、`sub`、`乘积取低 8 位`、`异或后取模`。命中率远高于你的预期。

:::

## 单字节 XOR 的致命缺陷

一旦确认「整段密文与同一个单字节密钥 XOR」，就可以**现场伪造任意响应**：

```c
BYTE K = cipher_nonce[4] ^ cipher_nonce[7];   // 从请求里现算
BYTE plain[67];
memcpy(plain, want, sizeof(want));            // 你想让客户端看到的内容
BYTE out[71];
out[0] = 0x47; out[1] = out[2] = out[3] = 0;  // 长度头
for (int i = 0; i < 67; i++) out[4 + i] = plain[i] ^ K;
send(c, out, 71, 0);
```

客户端解出来的明文和真服务器发的**一模一样**——它根本无法区分。

:::warning 这是防御方最该看的一段

如果密钥的推导依赖客户端**自己发出去的**明文字段，那么这条链上根本没有秘密。攻击者不需要任何密钥就能解密、也不需要任何密钥就能加密。

修法只有一个方向：**密钥必须来自双方都无法单方面决定的输入**（ECDH），并且响应必须带**服务端私钥签名**。

:::

## 什么时候该停止

区分「值得破」和「不值得破」，标准是**能否绕开**：

| 情况 | 决策 |
| --- | --- |
| 加密结果只影响一个判断分支 | 不用破，改客户端对结果的解释 |
| 加密结果参与后续计算（地址派生、功能开关） | 必须破，或者放弃 |
| 用非对称签名 | 放弃，去找别的路径 |

第二条是分水岭。如果解密出来的数据只是被 `if (code == 1)` 用一下，那加密再强也没意义——加密保护的是数据，不是判断。

## 一份检查清单

```text
[ ] 密文有可见周期吗       -> 固定密钥/短周期密钥
[ ] 256 个单字节密钥哪个打分最高
[ ] 已知明文能反推密钥吗
[ ] 多组样本能推出密钥公式吗
[ ] 密钥来自请求明文吗     -> 是的话加密等于没有
[ ] 解密结果影响什么       -> 只影响跳转？还是参与计算？
[ ] 有签名验证吗           -> 有就换路径
```

顺着这张表走，绝大多数「加密协议」在第三、四步就会现出原形。真正的密码学工程在逆向现场是罕见的——**罕见不等于没有，认出它并停下来，也是一种能力**。
